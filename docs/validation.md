# 検証記録と次の確認

**SSH切替後の自動テストはWindowsで合格済み。次の確認は、WindowsとMacの実機間での登録・Git転送・ホスト再起動である。**
この資料は、実装を評価する開発者が、確認済みの範囲と残る作業を判断するための記録とする。
利用手順は[README](../README.md)、各処理の採用理由は[設計](architecture.md)を参照。

## 確認済みの範囲

以下は2026-11-08のWindows開発環境での結果。

| 検証 | 結果 | 確認できたこと |
|---|---|---|
| 単体47件・統合7件 | 全54件成功 | 下記の登録・SSH認証・Git・停止処理 |
| fmt・Clippy・releaseビルド | 成功 | フォーマット、警告ゼロ、通常利用向けバイナリの生成 |
| Windowsの実Bluetoothアダプターでチャネル確保（SSH切替前の記録） | 成功 | 同時に自動起動したホストが4と5を確保。使用中の4の明示指定は失敗し、解放後の明示指定は成功 |

自動テストではBluetooth接続をインメモリまたはループバックのストリームに差し替え、実際の認証処理を通す。
Gitの統合テストは実際のCLI、Remote Helper、SSHクライアント／サーバー、Git子プロセスを実行する。3 MiBのバイナリでSSHの初期ウィンドウを超える転送も検証する。
実アダプターでは、自動割当・使用中チャネルの明示指定・解放後の確保を確認した。
表示コードに実際の割当番号が含まれることも確認済み。
検証用のプロセスはすべて終了済み。Ctrl+Cによる転送完了待ちの実機確認は、下記の合格項目に含める。

| テスト対象 | 主な確認内容 |
|---|---|
| モジュール内の単体テスト | 自動／明示選択と割当番号の検証、接続コードの誤入力・復元、登録名の競合・保存、鍵の保存と同時初期化、権限、誤番号・期限切れ、登録時の共有ID・SSH公開鍵の改変、切断 |
| `tests/git_roundtrip.rs` | コードと名前によるCLI登録、バイナリを含むclone/push/pull、競合push、rebase、fsck、再起動、権限解除、共有切替時の名前保持、失敗時の保存、二重起動 |
| `src/ssh/tests.rs` | SSHホスト鍵の不一致、秘密鍵による認証、exec前後の権限解除、不正コマンド・shell・転送・追加チャネルの拒否、遅延ブリッジの終端、停止・中断、Windows標準OpenSSHとの相互運用 |
| `tests/session_lifecycle.rs` | 登録待ちの取消、進行中のGit操作がSSHのexit-status・EOF・closeを完了してからの停止 |

再実行用コマンド：

```sh
cargo fmt --all --check
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo test --locked --features test-transport
cargo build --release --locked
```

CIにはWindows / macOS / Linuxで同じ検証を行うジョブを設定済み。
SSH切替後のmacOS・Linuxジョブの実行結果は確認待ちである。OpenSSH相互運用テストは `ssh` が未導入の場合のみスキップする。
Unixでは保存先の権限、MacではDispatch I/OとUnix socketによる遅延受信も追加テストの対象となる。

WindowsからのLinux向けcheckは、D-Busのクロスコンパイル環境が必要な段階で停止した。
Linuxでのビルドと自動割当は、Linux環境での確認が必要である。

## 実機で合格させる項目

**同じ登録名で再接続でき、転送を完了して停止・再開できることを合格条件とする。**
以下は実施待ち。まずWindowsホスト・Macゲストで確認し、両者を入れ替えて繰り返す。

SSH切替前の登録情報との互換性はない。既定では新しい `blugit/v2` を使い、独自の状態保存先を指定する場合も新しいディレクトリで登録し直す。
両端末で同じソースを通常インストールし、`blugit` と `git-remote-blugit` がともに1.0.0であることを確認する。
Bluetoothを有効にしてOSの利用許可に対応し、Wi-FiとEthernetを切った状態で実施する。
ホストが表示した12文字コードで `blugit join 接続コード demo` を実行し、Gitには `blugit://demo` を指定する。

| 操作 | 合格条件 |
|---|---|
| 検証用bareリポジトリを公開し、12文字コードで接続、6桁番号で登録 | 両端末で登録処理が完了する |
| ゲストでclone、commit、push | ホストのbare側に同じコミットとファイル内容が届く |
| ホストの作業コピーから変更をpushし、ゲストでpull | ゲストに同じ変更が届く |
| 転送中にホストでCtrl+Cを1回押す | 進行中の転送が正常終了し、その後ホストが終了する |
| 自動選択でホストを再起動 | 確保したチャネルのコードを表示する。コードが変わった場合も同じ名前で再登録すれば既存のoriginでfetch/pushできる |
| 明示指定したチャネルでホストを再起動 | 同じ接続コードを表示し、ゲストが既存のoriginで番号入力なしにfetch/pushできる |
| 別の状態ディレクトリで検証ホストを追加起動 | 使用中の番号を明示するとエラー。省略すると別の空きチャネルを確保する |
| `peers`でIDを調べ、`revoke`で権限を解除 | 新規接続が権限エラーになり、Gitデータは保持される |
| 別のリポジトリを公開 | 古いoriginと既存名での再登録は共有IDの不一致エラーになり、別名では登録できる |
| 同じリポジトリのチャネルを変更し、新しいコードで同じ名前に再登録 | originを変えずにfetch/pushできる |

特にMacホストでは、停止後に同じチャネルで再起動できることを確認する。
この結果を得た後に、PC間の無線転送とチャネル再利用を検証済みに更新する。
