# 検証記録と次の確認

2026-11-09時点。Windows／Macの両方向でBluetooth経由の登録・clone・push・pullと、チャネル変更後の自動再接続を確認した。
停止処理などには下記の未完了項目がある。実施した項目と自動テストだけの項目を分けて記録する。

利用手順は[README](../README.md)、採用理由は[設計](architecture.md)、探索方式は[チャネル自動解決](channel-resolution.md)を参照。

| 環境・検証 | 結果 |

| Windows：fmt、Clippy（全ターゲット・全機能）、通常のreleaseビルド | 成功 |

テスト用機能ではBluetoothをインメモリ／ループバックのストリームへ差し替える。
Git統合テストはCLI、Remote Helper、SSHクライアント／サーバー、Git子プロセスを実行し、3 MiBのバイナリ転送も含む。
通常ビルドではテスト用IPリスナーや経路設定を使わない。

| 対象 | 主な確認内容 |
|---|---|
| 登録・保存 | コード復元、誤番号・期限切れ、transcript改変、共有ID・SSH鍵の照合、保存の競合、原子的更新、Unix権限 |
| SSH・Git | 鍵不一致、署名、共有IDを含むSSHユーザー名、不正exec・shell・転送の拒否、権限解除、バイナリclone/push/pull、競合push、fsck、OpenSSH相互運用 |
| チャネル自動解決 | 新しい広告を古い保存済み番号より先に認証、未広告の番号は探索しない、広告がない場合のキャッシュ優先、同じ既知アドレスだけを探索、違うホスト鍵・同じ鍵の別共有を拒否、成功後だけ番号更新、失敗・競合時の登録保持、探索の期限 |
| 終了 | 登録待ちの取消、SSH exit-status・EOF・closeの完了待ち、遅延した末尾出力 |
| macOS固有 | Dispatch I/Oの遅延受信、プロセス間での番号競合・30番号の枯渇・解放、受付中の補助プロセス終了検知、SDPの世代属性・応答解析 |

再実行用コマンド：

```sh
cargo fmt --all --check
cargo clippy --locked --all-targets --all-features -- -D warnings
cargo test --locked --features test-transport
cargo build --release --locked
```

`BLUGIT_BLUETOOTH_DIAGNOSTICS=1` を指定すると、最初の接続と候補ごとの失敗理由、macOSの初期化状態を追加表示する。認証条件や登録の更新条件は変わらない。

OpenSSH相互運用は `ssh` が未導入の場合のみスキップする。
[main `d8a7fe0` のCI](https://github.com/mujuko/blugit/actions/runs/42496461515)で、Windowsの全66件、macOSの全72件、Linuxの全63件と、各OSのfmt・Clippy・releaseビルドが成功した。
直前のWindows CIで新しいRustのClippyが指摘した `chunks_exact_to_as_chunks` も、このコミットで修正済みである。

## 発見した不具合と修正

### macOSの同じ番号の二重割当

別の状態ディレクトリのホストが同じ番号を取得する事象を実機で再現した。
IOBluetoothのSDP登録結果だけでは、同じユーザーのblugit間の排他を保証できなかった。
アダプター別・番号別のファイルロックを補助プロセスが保持するよう変更し、明示指定の競合拒否、自動選択の異なる番号、終了後の解放・再確保を確認した。
この排他は同じOSユーザーのblugit間を対象とする。

補助プロセスが終了してもRustの受付が待ち続ける問題も修正し、制御ソケットの終了・エラーを監視するテストを追加した。

### Ctrl+CがGitと補助プロセスへ直接届く

実際のコンソール信号を送ったところ、ホストは転送完了待ちへ移ったが、Gitと受信hookも同じ信号で終了してpushが失敗した。
GitとmacOSの補助プロセスを独立したプロセスグループへ分離した。

Windowsでは、実際のCLI・SSH・Git・待機中の受信hookを使い、ネイティブの `CTRL_C_EVENT` を送るループバック検証が成功した。
ホストがhookの完了を待ち、受付停止後の出力をゲストへ届け、pushとホストがともに終了コード0で完了した。
修正後は実Bluetoothでも同じ試験が成功した。Macの事前fetchは1.422秒、pushは2.753秒で終了コード0となり、停止後のhook出力も届いた。
Windowsホストが信号後も生存して1接続の完了を待ち、解放後に終了コード0で終了した。
bare側のmainは送信した `48b24b7d33887bdd11b42ffa03c046034ffb8fb3` と一致し、fsckも成功した。

### Macからの再接続で初期化待ち

Windowsの検証ホストを番号5で再起動した後、Macの再接続が期限切れになる試行があった。
Mac補助プロセスのサンプルでは、RFCOMM接続呼出しより前の `WaitForBluetooth` に停止位置を特定した。
ローカルアドレス取得でも再現し、電源ONのままTCCにコード要件の不一致と許可プロンプトの保留を示すログがあった。
Rust本体を補助アプリへコピーする方式ではRust側の更新でも許可対象のコードが変わるため、専用の小さな実行ファイルへ分離した。
約84 KiBの専用ヘルパーはdebug／release・異なるビルド先でもSHA-256が一致し、Rust本体のバイト列だけを変える再ビルドと元へ戻す再ビルドでも一致した。
AppKitの起動処理と許可待ちの案内、電源・許可状態を区別するエラーを追加し、初期化前から親の終了を監視する。
ユーザーがmacOSのBluetooth利用を許可した後、既存demoへのfetchが1.268秒、終了コード0で成功した。
ログは `authorization=allowed` となり、初期化・SSH認証・Git転送まで完了した。アドレス・共有ID・チャネル6・alias・originは変更せず、再登録も行っていない。
ネイティブヘルパー自体の更新時にmacOSの許可が不要になる保証はしない。

## Macホスト／Windowsゲストの実Bluetooth検証

Macホスト／Windowsゲストでは、登録と初回cloneは成功した。
専用ヘルパー版でもWindowsからの3 MiBのpushとfresh cloneが成功した。
検証ブランチ `codex/validation-windows-20261108` のコミットは `0e7f4eac46019d3640c20ab4f93530eee62c9408`、バイナリのSHA-256は `a9aeed438f8dd1b764cc4907f53ca7b837f940c43e9ecb084b5b971b0dc931f1` で、再clone先でも一致し、fsckも成功した。
Macのローカル作業コピーから `mac-origin.txt` を追加し、同じ検証ブランチへpushした変更をWindowsでpullできた。
コミット `15b01f663f3f6a6f0441778abb2ca03a443b48ef`、Git blobのSHA-256、既存3 MiBファイル、fsckが一致した。

Macホストの受付を稼働させたまま、Macゲストとして既存のWindowsホストへfetchする操作も1.187秒・終了コード0で成功した。Macホストは終了せず、受付を維持した。
この確認では両方向のGit転送自体は重ねていない。

### 古いチャネルへの接続が後続の再接続を妨げる

Macホストを4から8へ移動したとき、Windowsからの逐次探索ではRFCOMM接続後にSSH応答を受け取れず、自動追従に失敗した。失敗時は既存aliasの4番と鍵・共有IDを保持した。
別の10番のホストでは直接認証が成功する一方、先に古い4番へ接続すると、その後の10番も失敗した。別スレッド・別プロセスに分けても再現し、Windowsの待機APIの変更でも解消しなかったため、これらの試験的変更は採用していない。

Windowsから既知Macのblugit UUIDだけを `LUP_FLUSHCACHE` 付きで照会すると、8番・4番・2番・1番など16件の広告が返った。
Mac側で所有レコードの削除が成功しても、停止後の再照会に古い広告が残った。広告だけでは受付の生存を判定できない。

修正版は、保存済み番号への接続より前に既知アドレスのSDPを再取得する。macOSホストは公開時刻を広告に含め、新しい候補から認証する。
広告が得られた場合は、保存済み番号や未広告の番号へ先に接続しない。広告がない環境では保存済み番号と認証付き逐次探索を使う。
この変更により、Windowsの既存aliasが4番から10番へ**再登録なしで自動更新され、fetchが2.772秒、次のfetchが0.522秒で成功**した。
Bluetoothアドレス・共有ID・保存した信頼情報・originは不変だった。SDPの情報は候補の順位付けに限り、採用と保存には従来どおりSSHホスト鍵と共有IDの認証を必要とする。
最終実装には診断用の全チャネル通知observerを含めず、自身の通知・番号・incoming方向が一致する接続だけを受け付ける。

## 残る実機確認

| 残る項目 | 合格条件 |
|---|---|
| Bluetooth転送中のCtrl+C | Windowsホストの1回目は成功。Macホストでの完了待ちと、2回目の中断を実機確認する |
| 最新のmacOS補助プログラム | 追加のBluetooth許可後、自動割当での再起動と既存Windows aliasからの追従、MacゲストのSDP経路を再確認する |
| 実機でのrevoke・共有切替 | 新規接続を拒否し、既存の登録とGitデータを保持する（自動テストは成功） |
| Linux | 実アダプターで割当・登録・Git転送（CIでのビルド・自動テストは成功） |
| ネットワークを切った環境 | Wi-Fi／Ethernetなしで同じ登録・Git操作が完了する |

今回の遠隔共同検証では制御用ネットワークを維持したため、完全なネットワーク切断試験は実施していない。
WindowsからMac広告を取得して認証するSDP経路は上記のとおり実施した。macOSゲスト側のSDP経路は更新版での実機確認を継続している。
最新のmacOS補助プログラムを通常インストールし、元のMacホスト10を0接続・終了コード0で正常停止した。更新版の起動はOSのBluetooth許可待ちで55秒後に終了し、まだ番号を確保していない。保存した端末・共有の情報は不変で、許可後に同じ状態から再開する。
SSH切替前の状態との互換性は用意しない。両端末を更新し、旧形式の状態を使っていた場合は新しい状態ディレクトリで登録する。
