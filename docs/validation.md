# 検証記録と次の確認

2026-11-09時点。Windows／Macの両方向でBluetooth経由の登録・clone・push・pullと、チャネル変更後の自動再接続を確認した。
停止処理などには下記の未完了項目がある。実施した項目と自動テストだけの項目を分けて記録する。
直近の実機比較はWindows build 26300.9711とmacOS 27.2（26B123、ビルド用SDK 26.5）で行った。SDKやOSの制約を他バージョンへ一律に当てはめない。

利用手順は[README](../README.md)、採用理由は[設計](architecture.md)、探索方式は[チャネル自動解決](channel-resolution.md)を参照。

## 発見した不具合と修正

### macOSの同じ番号の二重割当

別の状態ディレクトリのホストが同じ番号を取得する事象を実機で再現した。
IOBluetoothのSDP登録結果だけでは、同じユーザーのblugit間の排他を保証できなかった。
アダプター別・番号別のファイルロックを補助プロセスが保持するよう変更し、明示指定の競合拒否、自動選択の異なる番号、終了後の解放・再確保を確認した。
この排他は同じOSユーザーのblugit間を対象とする。

補助プロセスが終了してもRustの受付が待ち続ける問題も修正し、制御ソケットの終了・エラーを監視するテストを追加した。

### Ctrl+CがGitと補助プロセスへ直接届く

実際のコンソール信号を送ったところ、ホストは転送完了待ちへ移ったが、Gitと受信hookも同じ信号で終了してpushが失敗した。
GitとmacOSの補助プロセスを独立したプロセスグループへ分離した。

Windowsでは、実際のCLI・SSH・Git・待機中の受信hookを使い、ネイティブの `CTRL_C_EVENT` を送るループバック検証が成功した。
ホストがhookの完了を待ち、受付停止後の出力をゲストへ届け、pushとホストがともに終了コード0で完了した。
修正後は実Bluetoothでも同じ試験が成功した。Macの事前fetchは1.422秒、pushは2.753秒で終了コード0となり、停止後のhook出力も届いた。
Windowsホストが信号後も生存して1接続の完了を待ち、解放後に終了コード0で終了した。
bare側のmainは送信した `48b24b7d33887bdd11b42ffa03c046034ffb8fb3` と一致し、fsckも成功した。

Macホストでも実Bluetooth上のpush中、pre-receive hookへ到達してからホストの端末グループへ実際のSIGINTを1回送った。
ホスト・Git・補助プロセスは完了待ち中も生存し、12番の予約ロックも保持した。hook解放後は `mac-drain-output-after-listener-stop` がWindowsへ届き、pushが3.488秒・終了コード0で成功した。
ホストも終了コード0で終了し、補助プロセスの終了と予約ロックの解放を確認した。Mac bareの検証ブランチは送信した `39ab70e2b6c0044c607d5b995d6e4cfa60373858` と一致した。

### Macからの再接続で初期化待ち

Windowsの検証ホストを番号5で再起動した後、Macの再接続が期限切れになる試行があった。
Mac補助プロセスのサンプルでは、RFCOMM接続呼出しより前の `WaitForBluetooth` に停止位置を特定した。
ローカルアドレス取得でも再現し、電源ONのままTCCにコード要件の不一致と許可プロンプトの保留を示すログがあった。
Rust本体を補助アプリへコピーする方式ではRust側の更新でも許可対象のコードが変わるため、専用の小さな実行ファイルへ分離した。
約84 KiBの専用ヘルパーはdebug／release・異なるビルド先でもSHA-256が一致し、Rust本体のバイト列だけを変える再ビルドと元へ戻す再ビルドでも一致した。
AppKitの起動処理と許可待ちの案内、電源・許可状態を区別するエラーを追加し、初期化前から親の終了を監視する。
ユーザーがmacOSのBluetooth利用を許可した後、既存demoへのfetchが1.268秒、終了コード0で成功した。
ログは `authorization=allowed` となり、初期化・SSH認証・Git転送まで完了した。アドレス・共有ID・チャネル6・alias・originは変更せず、再登録も行っていない。
ネイティブヘルパー自体の更新時にmacOSの許可が不要になる保証はしない。

### SDP公開時の64ビット整数の変換

公開時刻のインメモリのSDKテストは成功していたが、実際に公開したレコードをWindowsで受信すると上下32ビットが逆転していた。
`1794153802861` ms の正しい値 `000001a1bbe66c6d` に対し、受信値は `bbe66c6d000001a1` だった。Mac側の公開済み要素も `NSNumber` ではなく `NSData` となり、数値取得はnilを返した。
所有する一時診断レコードで比較すると、64ビットの `NSNumber` と明示的なbig-endian `NSData` はどちらも同じ逆転が起きた。上位・下位の32ビット整数2個を並べたSDP sequenceだけが、両端末で正しい時刻となった。
この形式へ変更し、Windowsには受信した実レコードを使う回帰テストを追加した。広告は引き続き未認証の候補情報として扱う。
修正版の通常ヘルパーを13番で起動し、Windowsが受信した公開時刻 `1794155819235` とMacの読み戻し値も一致した。診断レコードだけでなく、実際のホストの広告でも確認した。

## Macホスト／Windowsゲストの実Bluetooth検証

Macホスト／Windowsゲストでは、登録と初回cloneは成功した。
専用ヘルパー版でもWindowsからの3 MiBのpushとfresh cloneが成功した。
検証ブランチ `codex/validation-windows-20261108` のコミットは `0e7f4eac46019d3640c20ab4f93530eee62c9408`、バイナリのSHA-256は `a9aeed438f8dd1b764cc4907f53ca7b837f940c43e9ecb084b5b971b0dc931f1` で、再clone先でも一致し、fsckも成功した。
Macのローカル作業コピーから `mac-origin.txt` を追加し、同じ検証ブランチへpushした変更をWindowsでpullできた。
コミット `15b01f663f3f6a6f0441778abb2ca03a443b48ef`、Git blobのSHA-256、既存3 MiBファイル、fsckが一致した。

Macホストの受付を稼働させたまま、Macゲストとして既存のWindowsホストへfetchする操作も1.187秒・終了コード0で成功した。Macホストは終了せず、受付を維持した。
この確認では両方向のGit転送自体は重ねていない。

最新ヘルパーのBluetooth利用を許可した後、MacゲストからWindowsの既存demo（6番）へのfetchも7.611秒・終了コード0で成功した。
MacのSDP照会は6秒以内に完了通知を受け取れず、候補なしとして保存済み6番へ接続した。端末・登録の3ファイル、alias・origin・Git設定は不変だった。

### 古いチャネルへの接続が後続の再接続を妨げる

Macホストを4から8へ移動したとき、Windowsからの逐次探索ではRFCOMM接続後にSSH応答を受け取れず、自動追従に失敗した。失敗時は既存aliasの4番と鍵・共有IDを保持した。
別の10番のホストでは直接認証が成功する一方、先に古い4番へ接続すると、その後の10番も失敗した。別スレッド・別プロセスに分けても再現し、Windowsの待機APIの変更でも解消しなかったため、これらの試験的変更は採用していない。

Windowsから既知Macのblugit UUIDだけを `LUP_FLUSHCACHE` 付きで照会すると、8番・4番・2番・1番など16件の広告が返った。
Mac側で所有レコードの削除が成功しても、停止後の再照会に古い広告が残った。広告だけでは受付の生存を判定できない。

修正版は、保存済み番号への接続より前に既知アドレスのSDPを再取得する。macOSホストは公開時刻を広告に含め、新しい候補から認証する。
広告が得られた場合は、保存済み番号や未広告の番号へ先に接続しない。広告がない環境では保存済み番号と認証付き逐次探索を使う。
この変更により、Windowsの既存aliasが4番から10番へ**再登録なしで自動更新され、fetchが2.772秒、次のfetchが0.522秒で成功**した。
Bluetoothアドレス・共有ID・保存した信頼情報・originは不変だった。SDPの情報は候補の順位付けに限り、採用と保存には従来どおりSSHホスト鍵と共有IDの認証を必要とする。
最終実装には診断用の全チャネル通知observerを含めず、自身の通知・番号・incoming方向が一致する接続だけを受け付ける。

追加のBluetooth許可後、Macを番号指定なしで起動すると1番で受付を開始した。しかしWindowsの10番からのfetchは、最初の1番を含む広告候補へのRFCOMM接続が期限切れとなり、131.915秒・終了コード128で失敗した。
aliasは10番を保持した。Macゲスト接続の終了後、SDPを再取得して1番だけを試した単発接続も8.009秒で期限切れとなった。広告時刻の修正と接続できない原因は分けて調査している。
同じ共有を11番へ移動すると、初回fetchは0.737秒で成功し、認証後にaliasが10番から11番へ更新された。信頼情報・共有ID・アドレス・originも不変だった。
直後の再fetchは136.425秒・終了コード128で失敗した。11番へのRFCOMM接続とMac側の通知・Unixストリーム接続までは到達したが、SSHの最初のデータを受信できず期限切れとなった。失敗後もaliasは11番を保持した。
12番への最初の接続で行ったpushと転送中の停止待ちは成功したが、これを同じ番号での再接続の解決とは扱わない。

広告時刻を修正した通常ビルドでは、12番から13番へのfetchが0.898秒、直後の再fetchが0.642秒で成功した。aliasは番号だけが変わり、信頼ファイルのSHA-256・共有ID・アドレス・originは不変で、fsckも成功した。
同じ修正版を番号指定なしで再起動すると1番になったが、Windowsからの接続は146.434秒・終了コード128で失敗し、aliasは13番を保持した。新しい1番の公開時刻と候補順位は正しく、広告時刻の不具合とは別に接続できない条件が残っている。
ローカルSDPのSPPサービス（UUID `0x1101`、handle `0x4f491101`）は番号取得APIでは1番と表示されたが、WindowsのSDP照会では同じhandleの広告が3番だった。この不一致があるため、競合を確定原因とは扱わない。
公開APIの自動割当比較では、0指定は0のまま、番号省略も補完されず、取得APIが例外を起こした。標準SPP UUIDを含めた別の比較では既存handleが返り、所有確認が足りないまま削除APIを2回呼んでしまった。両方の戻り値は0だった。以後は追加変更を止め、Mac・Windows双方でSPP登録が残ることを読み取り確認した。完全な試験前属性のバックアップはなく、属性差分と実動作への影響は断定できない。

この再発防止として、公開ごとにランダムなUUIDを属性 `0x0201` に含め、blugit単一クラス・そのUUID・番号が一致したSDK戻り値だけを採用する。削除直前にも再照合し、不一致のレコードは変更しない。
番号はSDKの取得関数へ任せず、ProtocolDescriptorListの構造・型・値域を直接検証する。欠落・不正値・例外では候補として採用しない。これらのテストはインメモリのSDKオブジェクトと削除カウンターを使い、実際のサービスへ追加・削除を行わない。
通知は既定の番号指定方式に加え、公開APIの全通知方式を内部診断用に選択できる。どちらも自分の通知・期待番号・incoming方向の照合を維持し、対象外の接続を閉じたりdelegateを変更したりしない。
保護を追加した通常インストール版は、ユーザーのBluetooth利用許可後に13番・既定の通知方式で起動した。6 MiB（3 MiBのファイル2個）を含むfresh cloneが49.559秒、commit後のpushが1.232秒、続くfetchが1.114秒で成功した。2ファイルのSHA-256とfsckが一致し、登録情報・信頼ファイル・originは不変だった。Mac bareの検証ブランチも送信した `75ea0f06040b235a26fd529e9a90e40f5dbbd583` と一致した。
同じバイナリを1番・既定の通知方式で起動すると、新しい1番の広告が最優先で取得されたが、fetchは146.682秒・終了コード128で失敗した。Mac側には着信通知がなく、aliasは13番、信頼ファイルのSHA-256も不変だった。同じ1番を全通知方式で比較しても146.704秒・終了コード128となり、着信通知はなかった。通知方式だけの変更は解決策として採用しない。Macの起動時刻は11月1日のままで、この比較間にOSの再起動はない。
既知MacへのRFCOMM UUID `0x0003` の読み取りSDP照会では、blugit・診断用レコード以外にCOM5（3番）とHandsfree Gateway（8番）を取得した。他サービスによる1番の広告は見つからず、競合を原因とは断定できない。
続く13番・全通知方式の対照も121.966秒で失敗したため、1番だけの問題とも断定しない。同じバイナリを14番・既定の通知方式へ移すと、aliasが13番から14番へ自動更新され、fetchが1.645秒、連続fetchが1.217秒で成功した。信頼情報・共有ID・アドレス・originを維持し、fsckも成功した。
削除成功を返した13番・1番の退役レコードは、Mac側の別プロセスからのローカル照会でも、元のランダムUUIDと番号を保持したまま見つかった。Windowsキャッシュだけの残留とは扱わず、SDKの削除・公開・受付の挙動を調査する。
対策として、ローカル広告の番号を除外して30番から降順に選び、番号のロック取得後にも一覧を再取得する修正を追加した。`01b9abe` のソースで全80テスト・fmt・Clippy・releaseが成功した。正常な型で番号0または番号省略の広告は、到達可能番号を名乗らないものとして一覧の集計時だけ区別する。認証候補・公開結果の所有確認では採用せず、未知型・不正値・照会失敗は公開前エラーにする。実機での新版の自動起動・再起動は次の確認とする。
この新版（ヘルパーのSHA-256先頭 `4ee5cb01`）を通常インストールした起動は、macOSのBluetooth再許可を待ち、55秒で終了した。READY・ローカル広告照会・SDP公開には到達していない。許可後も同じバイナリを使い、番号指定なしの起動と再起動を確認する。
