# blugitの設計

この資料は、実装を変更・レビューする開発者向けに、採用した方式、その理由、処理の流れを説明する。
利用手順は[README](../README.md)、動作確認の結果は[検証記録](validation.md)を参照。

## 基本方針：短いコードで接続し、登録後は名前を使う

**初回は6桁番号で端末鍵とSSH公開鍵を登録し、以後のGit操作はBluetooth上のSSHで認証・暗号化する。**

### ゲストとホスト

リポジトリを公開するPCをホスト、そこへ接続するPCをゲストと呼ぶ。

### 接続コードによる接続申請

ホストでbareリポジトリを指定して共有を開始すると、プログラムが接続コードを生成し、画面に表示する。

接続コードは `00MX-8433-A77D` のような英数字12文字で、ホストのBluetoothアドレスとチャネルを表す。

ホスト操作者が接続コードをゲスト操作者に伝える。
ゲスト側で `blugit join 接続コード 登録名` を実行すると、ホストに端末登録の申請が届く。

### 6桁番号による鍵交換

申請を受け付けたホストは、使い捨ての6桁番号を発行して画面に表示する。
ゲスト操作者はホスト操作者からこの番号を教えてもらい、ゲスト側に入力する。

双方のプログラムは、番号をもとに共通の暗号鍵を作り、その鍵を使った相互認証の成功によって番号の一致を確認する。
この方式により、番号そのものを送受信することなく番号の一致を確認できる。

### 鍵による認証と暗号化

認証に成功すると、ホストはゲストの公開鍵を保存する。
ゲストはホストの公開鍵と共有IDを、`join` で指定した登録名に対応付けて保存する。

以後は `git clone blugit://登録名` で登録を読み出し、保存済みの鍵を使ってGitの通信を相互認証・暗号化する。

## 接続先：初回の12文字コードと、登録後の名前を分ける

**初回に入力するのはホストへの接続コード、Gitに指定するのはゲストPCに保存した登録名とする。**

長いアドレスと共有IDを口頭で渡す負担を、接続先の符号化と登録情報の保存で減らす。

### 接続に使う情報

| 情報 | 取得する時点 | 用途 |
|---|---|---|
| Bluetoothアドレス・チャネル | 接続コードから復元したとき | ホストの接続口へ直接接続 |
| 共有ID | 登録時のホスト応答 | 公開中のリポジトリを識別。認証後に保存 |
| ホスト公開鍵 | 6桁番号による認証が成功したとき | 次回以降の接続相手を確認 |
| 登録名 | `join` の2番目の位置引数 | 保存した接続先を `blugit://登録名` から読み出す |

### 接続コード（12文字）の形式

48ビットのBluetoothアドレスと5ビットのチャネルを、11文字のBase32で表す。
先頭の余り2ビットは0に固定し、CRC-5の検査文字を1文字加えて12文字とする。

表記には紛らわしいI・L・O・Uを除いた英数字を使い、4文字ずつ区切る。

### 接続コードの誤入力検出

入力は大文字・小文字と区切りの有無を許容する。Oは0、IとLは1として扱う。
また、CRCにより、実際に接続する前にゲスト側で誤入力を（ある程度）検知できる。

### 接続コードと確認番号の役割

接続コードは公開する接続先情報である。
登録の許可には、申請ごとに発行する使い捨ての6桁番号を使う。

### 接続コードのチャネルによる接続

接続コードには、ホストが実際に確保したチャネル番号を含める。
初回登録では、ゲストはその番号を復元して接続するため、接続口を問い合わせるSDP検索を省略できる。

### 登録名の重複と再登録

登録名はゲスト側の状態ディレクトリ内で管理し、接続するホストと共有IDに結び付ける。
大文字と小文字は同じ扱いとする。

| 同じ登録名を指定する場合 | 動作 |
|---|---|
| 同じホスト・同じリポジトリ | 再登録できる。チャネルの変更も反映する |
| ホストまたはリポジトリが異なる | エラーで終了し、既存の登録を保持する。別名を使う |
| 別のゲストPC・別の状態ディレクトリ | それぞれ独立して同じ名前を使える |

ホストが公開リポジトリを切り替えた場合、既存名でのGit接続は共有ID不一致で終了する。

## チャネル：起動ごとに空き番号を確保し、変わったら認証で探し直す

**ホストは起動のたびに空いているチャネルを確保する。登録済みゲストは、番号が変わってもホスト鍵と共有IDの認証で新しい番号を見つける。**

### ホスト側のチャネル選択

| ホストの指定 | 動作 |
|---|---|
| `--channel` を省略 | チャネルを自動選択する。確保できなければエラー |
| `--channel 番号` を指定 | その番号を確保する。使用中ならエラー |

確保した番号が1〜30の範囲内にあり、明示指定した場合はその番号と一致することを確認してから接続コードを表示する。

### OSごとのチャネル確保

| OS | 自動選択の方法 |
|---|---|
| Windows | `BT_PORT_ANY` でbindし、`getsockname` で割当番号を取得する。[API仕様](https://learn.microsoft.com/en-us/windows/win32/bluetooth/bluetooth-and-bind) |
| macOS | ローカルのSDP広告に残る番号を除外し、30番から降順に候補を選んで公開する。[公開API仕様](https://developer.apple.com/documentation/iobluetooth/iobluetoothsdpservicerecord/publishedservicerecord(with:)) |
| Linux | RFCOMMソケットのチャネル0で動的割当を要求し、`local_addr` で割当番号を取得する。[API仕様](https://docs.rs/bluer/0.17.4/bluer/rfcomm/struct.Listener.html) |

### macOSで広告済みの番号を避ける理由

ホストは停止時に自身のサービスの登録解除を要求する。
ただし実機では、SDKが削除成功を返した後も広告が残り、同じ番号で再起動したホストへ接続できないことがあった。
別のRFCOMM実装にも[同じ番号を再利用できないという報告](https://dlech.github.io/aio-rfcomm/platforms/#each-channel-is-served-once)がある。OS内部の原因は特定していない。

そのため、削除要求の成功を空きの証拠とはせず、ローカル広告に残る番号を候補から除外する。

### macOSでの広告の読み取り

広告一覧の取得には非公開の読み取りAPIを使い、取得できなければ公開前にエラーにする。
SDKの番号取得APIは広告の値と一致しないことがあったため、属性の構造・型・値域を直接検証する。

### macOSでの番号の予約と公開

候補の番号ごとにプロセス間ロックを取り、広告一覧を再照会して、未使用なら公開する。
公開ごとにランダムなUUIDを付け、blugit単一クラス・UUID・番号が一致したレコードだけを採用・削除する。他サービスのレコードは削除しない。
このUUIDはローカルの誤操作防止用であり、ゲストの認証やSSHホスト鍵の照合を代替しない。

ロックの範囲や非公開APIへの依存条件は[チャネル自動解決](channel-resolution.md#ホスト側の番号確保)を参照。

### 再起動後の接続先の更新

自動選択では、ホストを再起動するとチャネルと接続コードが変わる場合がある。
登録済みゲストは、Windows／macOSではまず既知アドレスのSDP広告を再取得し、新しい広告の候補から認証する。
広告がなければ保存済みの番号を使い、失敗したら同じBluetoothアドレスの接続口を探し直す。

保存済みSSHホスト鍵と共有IDを認証できたときだけチャネルを更新し、共有ID・登録名・originは維持する。
チャネルの変更だけでは、6桁番号の入力や再登録を求めない。探索の期限やSDPとの関係は[チャネル自動解決](channel-resolution.md)を参照。

## 端末登録：6桁番号で端末鍵とSSH公開鍵を交換する

**番号から作った共通鍵で双方の端末鍵を認証し、改変されていない登録情報だけを保存する。**

### 登録の手順

1. ゲストが端末情報を送る。ホストは共有IDを応答し、6桁番号を発行する。
2. ホスト操作者が登録を許可する場合は、ゲスト操作者に番号を伝え、入力してもらう。
3. SPAKE2で共通鍵を導出し、その鍵を使うNoise XXpsk3で双方の端末鍵を確認する。SSH公開鍵もtranscriptに含め、この認証で結び付ける。
4. ゲストが登録を確定する。ホストはゲストの端末公開鍵とSSH公開鍵を保存し、受理を返す。
5. ゲストがホストの端末公開鍵・SSH公開鍵・共有IDを保存して応答し、ホストが完了を返す。
6. ゲストが登録名と接続先の対応を保存する。

登録成功を表示するのは、ホストの完了応答を受け取り、ゲストが登録名を保存した後とする。
既存の登録名で再登録する場合は、ホストが応答した共有IDと保存済みIDの一致も確認する。

### 登録メッセージと認証対象

登録要求は `BLUGIT/2\n` と最大4096バイトの型付きJSONで送る。Noiseと独自の暗号化レコードは、この初回登録だけに使う。
要求・応答、接続上の役割、共有ID、双方の端末情報とSSH公開鍵、ホストのランダム値を認証対象（transcript）に含める。
通信中に共有IDやSSH公開鍵が改変されると、番号による認証が失敗し、登録を保存しない。

### 確認番号の制限

| 制限 | 値 |
|---|---|
| 有効期限 | 180秒 |
| 照合回数 | 1回 |
| 同時申請 | 1件 |
| 発行間隔 | 最低10秒 |

これらの制限で、番号を試せる回数を抑える。

### 途中で失敗した登録

途中切断や保存の失敗で、片側だけ、または鍵だけが保存済みになる場合がある。
新しい番号で再登録すれば、保存を完了できる。

## Git接続：Bluetooth上でSSHを直接動かす

**RFCOMMのバイトストリーム上でSSHクライアント／サーバーを直接動かし、登録済みの鍵で相互認証する。**

### アプリに組み込んだSSH

`russh` をアプリに組み込み、OSのsshd・IPリスナー・OSアカウント・ssh-agentの設定を必要としない。
同じBluetooth接続口で、登録用の `BLUGIT/2` と `SSH-2.0` を先頭バイトで振り分ける。
Git転送で登録用のNoise処理を通すことはない。

### SSHの相互認証

ゲストは登録済みのSSHホスト鍵と完全一致する鍵だけを受け入れる。TOFUや対話的な自動承認は行わない。
SSHのユーザー名は `共有ID.端末ID` とする。
ホストは、共有IDが公開中のものと一致し、その端末IDに登録したEd25519鍵で署名されていることを検証する。

### 登録用の鍵とSSH用の鍵

端末識別と登録に使うX25519鍵と、SSHの署名に使うEd25519鍵は、独立した乱数で生成する。
鍵や端末名を申告するだけではSSH認証は成功せず、対応するSSH秘密鍵の所持が必要になる。

### 許可するGit操作

1接続につきsessionチャネル1つ、Git exec 1回だけを受け付ける。
execは次の2つの完全一致のみ許可し、共有IDをホストの公開中リポジトリと照合する。

```text
git-upload-pack '共有ID'
git-receive-pack '共有ID'
```

共有IDを仮想パスとして扱い、ゲストが指定したファイルパスを開くことはない。
コマンドをシェルに渡さず、検証済みのサービス名とホストのbareパスをGit子プロセスへ直接渡す。
shell・PTY・環境変数・サブシステム・ポート転送は許可しない。

### 同時接続数

同時接続は最大16件とし、上限に達している間の新しい接続は閉じる。

## アクセス権：リポジトリごとに端末の公開鍵を登録する

**共有IDが一致し、接続相手が登録済み公開鍵に対応する秘密鍵を持つ場合だけ、Git操作を許可する。**

### 操作するリポジトリの決定

ゲストはSSH execで共有IDとGit操作の種類を要求し、ホストは起動時に確定したbareパスをGitに渡す。
これにより、登録名に保存したリポジトリと、実際に操作するリポジトリを一致させる。

### 端末の識別

端末の識別子は公開鍵、端末名は操作者向けの表示名とする。
同名の端末も鍵で区別でき、名前変更後も権限を維持できる。
コミットの作者名・メールアドレスは端末登録とは関係なく、Gitの設定に従う。

### 権限解除を反映する時点

ホストはSSH公開鍵の提示時、署名の検証後、Git execの直前に登録を確認する。

| 解除された時点 | 動作 |
|---|---|
| SSH認証中・Git execを許可する前 | 認証またはexecを拒否する |
| Git execを許可した後 | 開始済みの操作は継続し、以後の接続で拒否する |

別リポジトリへ切り替えた場合、その共有に登録がなければSSH認証で拒否し、登録があってもexecの共有ID不一致で拒否する。

## 転送完了：SSHの終了状態とチャネル終端を確認する

**Gitの出力と終了コードはSSH標準の仕組みで送り、ゲストは相手への到達を確かめてから終了する。**

Gitの標準出力はSSH channel data、標準エラーはextended data（種別1）で転送する。
終了コード・入力終端・チャネル終端にはSSHの `exit-status`・EOF・closeを使う。

```text
ホスト                                  ゲストのRemote Helper
  |── Git stdout / stderr ───────────────→|
  |── exit-status → EOF → channel close ─→|
  |←─ channel closeの応答 ────────────────|
  |←─ keepalive@openssh.com（応答要求）────|
  |── SSH global requestの応答 ──────────→|
  |                                      | Gitの終了結果を返して終了
```

### ゲスト側の完了判定

Remote Helperはexit-status・EOF・closeのすべてを受け取り、closeの応答を送った後のSSH往復を確認する。
ローカルでflushしても、末尾のデータがBluetooth補助プロセスに残っている場合がある。往復を待つことで、相手に届く前に接続を破棄しないようにする。
終了通知の欠落、チャネル終端前の切断、SSH暗号認証の失敗は正常完了として扱わない。

### ホスト側の待機

ホストはGitの出力と終了通知を送信待ちに積んだ後も、SSH接続の終了を最大10秒待つ。
この段階の接続終了は、ゲストがGitの結果を受理した証明としては扱わない。

### Git子プロセスの扱い

ゲストのEOFを受け取ったら、ホストはGit子プロセスの標準入力を閉じる。
clone・pullは `git upload-pack`、pushは `git receive-pack` を、親の `GIT_*` 環境変数を除去して起動する。
リポジトリ設定・受信hook・競合判定はGitに任せる。

## ホスト停止：受付を閉じ、進行中のGit操作を完了させる

**1回目のCtrl+Cは転送完了を待つ停止、2回目は即時中断とする。**

### 1回目：転送完了を待つ

接続受付を閉じ、認証・登録待ちを取り消す。
Git execを許可済みの接続は、Gitの出力・終了通知とSSH接続の終了まで待つ。
Git子プロセスとmacOSのBluetooth補助プロセスは別のプロセスグループで起動し、端末のCtrl+Cが直接転送を中断しないようにする。
macOSでは受付を閉じても、進行中の接続がある間は補助プロセスと番号の予約を保持する。

### 2回目：転送を中断する

残りの接続タスクをすべて中断する。
タスクの破棄に伴ってSSHのバックグラウンド処理も取り消され、ハンドラーが持つGit子プロセスも終了する。

## 永続化：再起動で識別と権限を維持する

**端末鍵とアクセス権はユーザーの状態ディレクトリに保存し、Gitリポジトリには共有IDを記録する。**

### 保存する情報

端末鍵はその状態ディレクトリを使う端末を、共有IDはそのリポジトリを識別する。
鍵と共有ID、接続先を維持すれば、再起動後も同じ登録名とoriginを使える。

| 保存対象 | 保存内容と役割 |
|---|---|
| 端末情報 | X25519鍵・独立したSSH Ed25519鍵・表示名。端末識別とSSH認証に使用 |
| ゲスト側のホスト登録 | Bluetoothアドレスと共有IDに対応するホスト鍵。接続相手の照合に使用 |
| ゲスト側のローカル登録名 | 名前に対応するアドレス・チャネル・共有ID。Git接続時の解決に使用 |
| ホスト側の共有情報 | 共有ID・正規化したリポジトリパス・許可済み端末。Gitの対象と権限の決定に使用 |
| リポジトリ内の `.blugit-share.json` | 共有ID。ファイル移動後の識別に使用 |

### リポジトリのコピーと移動

同じ状態ディレクトリで共有を登録する際、保存済みの元パスが存在するかどうかで判定する。

| 状態 | 扱い |
|---|---|
| 元パスが残り、別パスに同じIDがある | コピーとして新しいIDを割り当て、独立した共有にする |
| 元パスが消え、別パスに同じIDがある | 移動としてIDと権限を引き継ぐ |

### 保存形式と保存先

状態ファイルはJSONで、端末情報はスキーマ2、それ以外はスキーマ1とする。
既定の保存先はユーザーデータディレクトリの `blugit/v2` とする。
環境変数 `BLUGIT_HOME` で変更でき、`blugit` コマンドでは `--state-dir` も指定できる。

### 原子的な更新とロック

一時ファイルへの書き込み・fsync・置換で更新する。Unixでは親ディレクトリも同期する。
プロセス間ロックで鍵の初期化、共有の登録、権限の更新を直列化し、同じ状態ディレクトリで起動できるホストも1つに限る。
登録名は名前ごとのロックで排他し、同時登録と別リポジトリへの上書きを防ぐ。

### 破損した記録の扱い

壊れた鍵や不整合な記録を読み込んだ場合は、対象の操作をエラーで終了する。

### 保存先の権限と秘密値の破棄

Unixの状態ディレクトリは0700、ファイルは0600。Windowsは保存先のACLを継承する。
bareリポジトリには、既存の権限を保ったまま `.blugit-share.json` を追加する。
アプリが保持する秘密鍵レコードと使い捨て番号は、破棄時にメモリを上書きする。

## モジュール：OS接続を差し替えて認証とGitを検証する

**OSごとの通信実装をバイトストリームの境界に閉じ込め、その上の認証・権限・Git処理を共通化する。**

### テストで差し替える境界

テストではこの境界にインメモリ接続やループバック接続を渡す。
実機を使う範囲を通信部分に絞り、登録からGit CLIの往復まで自動検証できる構成とした。

### モジュールごとの責務

| モジュール | 担当 |
|---|---|
| `cli` / `helper` | ユーザーの操作、Git Remote Helperの入出力 |
| `model` / `endpoint` / `connection_code` | 端末・共有ID・接続先の型、12文字コードの符号化と入力検証 |
| `storage` | 端末鍵、ホスト登録、ローカル名、共有情報、権限の保存 |
| `client` / `resolver` / `protocol` | 認証によるチャネル再解決、番号による初回登録、端末鍵とSSH公開鍵の交換 |
| `ssh` | SSHホスト鍵照合、公開鍵認証、Git execの許可、SSH接続の終了と取消 |
| `server` | 接続の受付、上限管理、停止時の待機と中断 |
| `git` | 許可コマンドの検証、Git子プロセス、SSHチャネルとの入出力・終了状態の中継 |
| `platform` / `native/macos.m` | Windows Winsock、macOS IOBluetooth、Linux BlueZによるバイト転送 |

### macOSのBluetoothヘルパー

macOSではネイティブのBluetooth処理を専用の小さな実行ファイルとしてビルドし、Rustバイナリへ埋め込む。
起動時にアプリbundleとして取り出し、AppKitを初期化してからOSのBluetooth許可を要求する。

ヘルパーはCargoのプロファイルと独立した設定でコンパイルするため、Rust本体だけの変更では許可対象のコードは変わらない。
ヘルパー自体を更新すると、macOSが新しいコードとして扱い、許可を求め直す場合がある。許可待ち・拒否・電源オフは別々のエラーとして報告する。

## セキュリティ上の制約と参照資料

### 依存ライブラリによる制約

採用した `spake2 0.4` は、独立監査未実施・タイミング攻撃保護未保証と公式に記載されている。

メモリ上書きの対象はアプリが管理する値であり、依存ライブラリ内部のコピーは対象外である。
